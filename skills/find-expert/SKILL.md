# 「◯◯に詳しい人」を探す

`$ARGUMENTS` のトピックについて、**誰が詳しいか**を探す。単なる情報検索 (`search-lab`) と違い、
最終的な答えは **人物のリスト + その人が詳しいと言える根拠(リンク)** になる。

## まず振り分け

- 「◯◯について知りたい / 経緯を追いたい」 → `search-lab` へ。
- 「◯◯はいつ?」 → `find-schedule` へ。
- 「◯◯を話しているチャンネルは?」 → `find-channel` へ。
- 「**誰**が詳しい / 誰に聞けばいい / 誰がやったことある」→ このまま続行。

## 手順

### 1. 検索語を組み立てる

トピックから 2〜4 個の検索語を用意する。**略称・正式名称・英語/日本語・関連語**を混ぜる。

- 例: 「MCP」→ `MCP`, `Model Context Protocol`, `MCP サーバー`
- 例: 「トーラス」→ `トーラス`, `torus`, `トーラス上` (グラフ描画文脈なら `torus layout` も)
- 例: 「根付き木」→ `根付き木`, `rooted tree`, `木構造`

期間は既定で **今日の 2 年前**〜今日。専門性は蓄積するので、日程系スキルより広く取る。
以降 `<SINCE>` はその日付 (`YYYY-MM-DD`)。

### 2. esa を検索して「記事の著者」を集める

esa MCP の `esa_search_posts` (`teamName` = `.env` の `ESA_DEFAULT_TEAM`) で各検索語を検索する。
**記事を書いている人は最も強い根拠**なので必ず先に取る。

得られた記事を、次の共通ヒット形の JSON 配列にして一時ファイルに書く
(`created_by.screen_name` ではなく **`updated_by`/`created_by` の表示名**を `author` に入れる):

```json
[
  {
    "source": "esa",
    "title": "記事タイトル",
    "url": "https://<team>.esa.io/posts/123",
    "snippet": "本文の関連する箇所を 200 字程度で",
    "author": "書いた人の表示名",
    "timestamp": "2026-04-01T00:00:00Z"
  }
]
```

### 3. Slack / Discord / Calendar / GitHub / Drive を検索して人物ごとに畳み込む

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/bin/find-expert.mjs" "<検索語>" \
  --since <SINCE> --top 8 --evidence 4 \
  --extra-hits /tmp/esa-hits.json --text
```

- 既定ソース = `.env` で設定できている全ソース (calendar / slack / discord / github / drive)。
  `--source slack,discord` のように絞ってもよい。
- 検索語が複数あるときは **語ごとに実行**し、結果を突き合わせる (同じ人が複数語で上位に来たら強い)。
- 出力の見かた:
  - `score` … ソースの重み × 鮮度 × 検索語の濃さ の合計。**機械的なヒント**であって順位そのものではない。
  - `countBySource` … 複数ソースに顔を出す人ほど本物の可能性が高い。
  - `evidence[]` … その人が詳しいと言える根拠。**必ず中身を読むこと**。
- `--alias "しらしょーじ=Shirashoji"` で表記ゆれを名寄せできる。
- Bot / GitHub 連携の自動投稿は既定で除外される (`--include-bots` で含む)。

### 4. 根拠を読んで判断する

`score` を鵜呑みにせず、`evidence` の抜粋を読んで **本当にそのトピックの話か** を確かめる。

- 単に単語が出てくるだけ (「MCP って何?」と質問しているだけ) → **詳しい人ではない**。降格する。
- 説明している / 実装している / 記事を書いている / 質問に答えている → **詳しい人**。
- 発表・ゼミ資料の作成者 → 詳しい人。
- 1 件しか根拠が無い人は「候補」止まりにする。

### 5. 答える

次の形でまとめる。

1. **結論** — 「〜については ◯◯さんが詳しそうです」(1〜3 名)。断定できないときは断定しない。
2. **各人について**:
   - なぜそう言えるか (1〜2 文)
   - 根拠リンク (esa 記事 URL / Slack permalink / Discord メッセージ URL / GitHub URL / Drive リンク)
     と、その中身の**要約または引用**。ユーザーがリンクを開かなくても内容が分かるようにする。
   - 主な活動場所 (チャンネル名 / リポジトリ名)
   - 直近いつ頃その話をしていたか
3. **次の一手** — 「#〜 チャンネルで聞くとよい」「この記事を先に読むとよい」を 1〜2 個。
4. **見た範囲** — 検索したソース・期間・スキップしたソース・カバレッジを必ず書く。

## 注意

- **人物評価を扱う**ので、書き方は事実ベースにする。「詳しい」は
  「このトピックについて書いている / 実装している」という**観測事実**として述べ、
  能力の断定や比較 (「◯◯さんより詳しい」) はしない。
- 見つからないときは正直に「この範囲では特定できなかった」と書き、
  検索語を変える / 期間を広げる / Bot 権限を足す などの次の手を提案する。
- 投稿・DM 送信などの副作用操作はこのスキルではしない (調査のみ)。
  「本人に聞いてみますか?」と提案するのは可。実際に送るのはユーザーの仕事。
- カバレッジの既知の制約:
  - Discord は Bot に閲覧権限のあるチャンネルのみ (権限が無いチャンネル数は警告に出る)。
  - Slack は `SLACK_USER_TOKEN` の所有者が見えるチャンネルのみ。
  - GitHub の code 検索は期間指定ができない。また code のヒットは著者・日付が API から返らないので
    最新コミットから補完している(先頭 10 件まで)。
    トークンの権限が足りずに GitHub が丸ごと落ちている場合は
    `node ${CLAUDE_PLUGIN_ROOT}/scripts/bin/check-github-token.mjs` の実行を案内する
    (詳細は `docs/GITHUB-TOKEN.md`)。
  - Drive は `drive.readonly` スコープが必要 (未許可なら `auth-google.mjs` の再実行を案内する)。
